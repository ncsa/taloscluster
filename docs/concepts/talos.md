# Why Talos Linux

[Talos Linux](https://www.talos.dev/) is a Linux distribution built for one job: running Kubernetes. There is no shell, no SSH, no package manager and no writable root filesystem. The whole machine is described by a single [machine configuration](https://docs.siderolabs.com/talos/latest/reference/configuration/overview) and managed over a gRPC API with [`talosctl`](https://docs.siderolabs.com/talos/latest/reference/cli), the same way you manage Kubernetes itself with `kubectl`.

taloscluster is a small tool that turns a `cluster.yaml` into a Talos cluster on OpenStack or Proxmox. If you want a supported product for managing many clusters, with a UI, access control and hosted or self-hosted control plane, use Sidero's [Omni](https://www.siderolabs.com/platform/saas-for-kubernetes/) instead. taloscluster is for the case where you want the same Talos benefits on your own cloud with nothing but a git repo and a CLI.

## Small attack surface

Talos ships only what Kubernetes needs: the kernel, containerd, kubelet and a handful of Go services. Because there is no shell or SSH daemon there is nothing to log in to, and the API only accepts mutual TLS with the cluster's own certificates. The root filesystem is read-only and squashfs, the image is signed, and every setting lives in the machine configuration rather than in files someone edited on the host. Anything extra, such as a GPU driver or the guest agent, is added as a signed [system extension](https://docs.siderolabs.com/talos/latest/build-and-extend-talos/custom-images-and-development/system-extensions) baked into the image. See the [Talos security philosophy](https://docs.siderolabs.com/talos/latest/learn-more/philosophy) for the full argument.

taloscluster narrows the surface further. The [`security`](../configuration/security.md) allowlists configure the selected provider's firewall (the OpenStack security group or the Proxmox per-VM firewall) and the per-node Talos [ingress firewall](https://docs.siderolabs.com/talos/latest/networking/ingress-firewall) on every node, bare metal included. TCP ports 80 and 443 are open by default until claimed by a rule; intra-cluster traffic — from every L2 the cluster's nodes sit on — and required protocol exceptions are also allowed. API allowlists restrict other sources. On Proxmox, the operator must enable the datacenter firewall for the provider rules to take effect. The machines can also live on a private network with no public address at all, reachable for management only through [tailscale](machines.md#reaching-the-nodes), a WireGuard-based VPN mesh, while the API VIP and the ingress addresses stay the only things exposed. [Day 0](lifecycle.md#day-0-design) walks through the address and port choices.

One exposure the firewalls cannot reach is the machine configuration itself, which carries the cluster's secrets — the CA keys, the node join tokens and the tailscale auth key — and travels through the provider's first-boot channel. On OpenStack that channel is Nova `user_data`, which the metadata service keeps serving at `169.254.169.254` for the instance's whole lifetime, an address every pod's egress reaches masqueraded behind its node: an unprivileged pod could read a control plane's configuration and take over the cluster. taloscluster therefore blocks that address in the OpenStack security group itself — Neutron's default allow-all egress rules give way to rules permitting every destination except the metadata address, which cuts node and pod traffic off from it under any CNI and in every namespace — with a NetworkPolicy in the bootstrap manifests as defence in depth; the details and their limits are stated in the [OpenStack provider guide](../providers/openstack.md#machine-configuration-and-the-metadata-service). Proxmox detaches the cloud-init ISO that carried the configuration once every node is Ready, and bare metal never exposes one on the network at all.

The disks answer for what a firewall cannot reach at rest: taloscluster encrypts the `STATE` and `EPHEMERAL` partitions of every machine it installs with LUKS2, keyed with a passphrase generated into `talossecrets.yaml` beside the CA — the same file, and the same backup discipline, as the rest of the cluster's identity. A stolen disk or volume snapshot then reads as ciphertext without the cluster directory. The protection has a stated edge: the passphrase travels with the machine configuration through the first-boot channel above, so whoever can read that channel can read what it unlocks — on OpenStack that is the same `user_data` exposure the security group's egress rules limit, while on Proxmox the ISO is detached after install and the passphrase sits on no storage the hypervisor keeps. The settings reach a machine only when it is installed, so a cluster created before this hardening keeps its unencrypted disks — pushing encryption settings at a machine installed without them would stop it booting — and once the secrets carry the passphrase, every machine the cluster installs encrypts its disks.

Proxmox machines boot with Secure Boot enforced. The VM is created with UEFI and an EFI disk whose variable store starts empty — no pre-enrolled vendor keys, which is what leaves the firmware in setup mode — and the boot ISO is the Image Factory's Secure Boot image, whose bootloader enrolls the factory's own signing keys on that first boot before starting the installed system as a signed UKI. The installer image is the SecureBoot variant for the same reason, so a node only ever runs a kernel the factory signed, and `talosctl upgrade` keeps the same SecureBoot installer reference, so an upgraded node rebuilds its UKI under the same enrolled keys. That holds for a node whose firmware enrolled the keys, and converge checks before it assumes it: the releases before Secure Boot support created VMs that booted the plain ISO, so those machines run with Secure Boot unenforced and the UKI boot path on their never-enrolled firmware is unverified. Before an upgrade, converge reads the security state the node reports (`talosctl get securitystate`), keeps the plain installer for a node that says Secure Boot is not enforced, and hands the SecureBoot installer only to one whose firmware reports the keys. Bare metal keeps the plain ISO: that enrollment is only automatic in a virtual machine, and a Secure Boot ISO on real hardware would stop in the boot menu waiting for keys nobody enrolled.

The bootstrap manifests no longer follow a URL, either. The kubelet serving certificate approver and metrics-server definitions are vendored into the generator and applied as inline manifests, so what a control plane runs is fixed by the taloscluster release that built its configuration — no moved GitHub tag can swap them, which matters because the approver holds the RBAC that approves kubelet serving certificates. Bumping either is a deliberate update to that vendored copy.

## Upgrades are boring

An [OS upgrade](https://docs.siderolabs.com/talos/latest/configure-your-talos-cluster/lifecycle-management/upgrading-talos) in Talos is `talosctl upgrade` to a new image: the node pulls it, switches the A/B boot partition, reboots, and rolls back on its own if the new system does not come up. A Kubernetes upgrade is `talosctl upgrade-k8s`, which walks the control plane and kubelets through the new version. Draining and restarting nodes can interrupt workloads; availability depends on replicas, disruption budgets, and spare capacity.

With taloscluster both are a one-line edit. Bump [`talos.version`](../configuration/general.md#talosversion) or [`kubernetes.version`](../configuration/general.md#kubernetesversion) in `cluster.yaml`, run `taloscluster converge`, and existing nodes are upgraded one at a time before any new ones are added. Kubernetes moves one minor at a time and Talos goes first when both change. Talos publishes a [support matrix](https://docs.siderolabs.com/talos/latest/getting-started/support-matrix) of which Kubernetes versions each release supports, and a `kubernetes.version` outside the pinned release's range is refused when the configuration loads, just as a `talos.version` older than what the cluster runs is refused in converge's validate phase.

## One pod network across networks

Talos ships [KubeSpan](https://docs.siderolabs.com/talos/latest/networking/kubespan), a WireGuard overlay that taloscluster turns on on every node when [`talos.kubespan`](../configuration/general.md#taloskubespan) enables it. Each node gets an address on the encrypted overlay, peers find each other through Talos's discovery service, and pod traffic between nodes rides the overlay — which is what lets one cluster span layer-2 networks, VMs on a provider's network and bare metal on its own, wherever an IP route connects the two sides. The firewalls open KubeSpan's UDP/51820 from every node L2 beside the intra-cluster rules, so peers on another L2 can complete their WireGuard handshakes (see [always allowed](../configuration/security.md#always-allowed)).

KubeSpan carries only that overlay traffic. The Kubernetes API VIP is never on it — the kubelet on every node still reaches `kubeapi_vip` directly — and management traffic follows the [management access path](machines.md#reaching-the-nodes), so a cluster whose nodes sit on more than one network still needs plain routing between them: where the VM provider's network is an overlay the metal side cannot see (Proxmox SDN, OpenStack), the API VIP must be made reachable from the metal L2 with a floating IP or exit-node routing, and nodes with no direct internet access must hand the discovery service a proxy through `machine.env`. The reachability requirements are spelled out under [`talos.kubespan`](../configuration/general.md#taloskubespan).
